# 技术决策记录

每条记录写清楚背景、决定、考虑过的替代方案和代价。

## ADR-1 生成物限定为单文件 HTML

- **背景**：生成要在几十秒内稳定出结果，并且能即时预览、发布。
- **决定**：生成 Tailwind CDN + 原生 JS 的单文件 HTML。
- **替代方案**：React 多文件工程 + WebContainer 或服务端构建。
- **代价**：不支持 npm 依赖和复杂工程。版本存储、预览、发布都因此简化为"一段 HTML"，扩展路径见 [roadmap](roadmap.md)。

## ADR-2 顺序流水线 + 共享上下文，而不是自主规划循环

- **背景**：要体现多智能体协作，同时保证耗时可预期、出错好定位。
- **决定**：固定顺序的流水线，`when()` 决定出场，`halt` 提前结束；成员通过共享上下文（`artifacts`、`notes`）传递产物。
- **替代方案**：让领导者智能体自主规划和多轮调度。
- **代价**：灵活性较低。但每一步可观察、可测试，扩展点（新角色、条件出场）已经覆盖了大部分需要。

## ADR-3 规划用 JSON，代码用分隔标记

- **背景**：规划类产出需要被程序消费；代码需要边生成边预览。
- **决定**：规划用 JSON 模式 + zod 校验 + 失败重试一次；代码用 `<<<FILE>>>` 标记包裹的纯文本流，迭代用 SEARCH/REPLACE 补丁。
- **替代方案**：全部 JSON，或全部自由文本。
- **代价**：需要维护一个容错解析器（兼容多包一层代码块、没按格式输出等情况），已用单元测试覆盖。

## ADR-4 版本存全量快照

- **背景**：需要查看、回滚、发布任意版本。
- **决定**：每个版本存完整 HTML，回滚 = 复制旧版本为新版本。
- **替代方案**：存 diff。
- **代价**：存储略多（单文件通常 10 到 40 KB，可以忽略），换来读取和回滚都是一次查询，历史只追加不改写。

## ADR-5 只有生成接口走服务端，其余靠 RLS

- **背景**：减少后端代码，同时保证数据隔离。
- **决定**：前端直接用 Supabase SDK 做增删改查，权限全部写在 RLS；服务端只负责需要保密 Key 的模型调用，并且也用用户会话访问数据库。
- **替代方案**：每个操作写一个 API。
- **代价**：业务规则需要能用 SQL 表达；复杂的跨表事务以后可以改用数据库函数。

## ADR-6 沙箱不加 allow-same-origin，用运行时替代 localStorage

- **背景**：生成的代码不可信，但生成的应用需要持久化数据。
- **决定**：iframe 不加 `allow-same-origin`；注入运行时，通过 postMessage 把 Storage 读写交给父页面按项目保存。
- **替代方案**：加上 `allow-same-origin`（会暴露主站 Cookie），或给生成的应用提供后端存储。
- **代价**：数据存在浏览器里，换设备不同步。云端数据列为后续扩展。

## ADR-7 游客模式使用 Supabase 匿名登录

- **背景**：降低体验门槛，提问不应该强制注册。
- **决定**：未登录用户创建项目时自动匿名登录，之后可以在同一用户 id 上绑定邮箱密码。
- **替代方案**：未登录时数据存本地，注册后迁移。
- **代价**：需要在 Supabase 打开匿名登录，并给游客单独限流。RLS、限流、数据结构全部复用，绑定账号不需要数据迁移。

## ADR-8 自定义智能体是数据，不是代码

- **背景**：用户要能定制工作流，但不能执行任意代码。
- **决定**：自定义智能体只是一份配置（职责说明、出场位置、参与流程），由 `defineCustomAgent` 变成标准的 Agent；它只产出建议，由工程师落地。
- **替代方案**：允许用户写提示词直接改代码，或上传脚本。
- **代价**：自定义智能体不能直接改代码，但风险可控，输出格式统一，前端用同一种卡片渲染；配置可以直接序列化，为智能体市场留好了基础。

## ADR-9 统一错误码 + 请求 id

- **背景**：模型服务的失败方式很多（Key、余额、限流、超时、输出不合法），用户需要知道该怎么办，开发者需要能定位。
- **决定**：服务端把所有异常归类为 `AppError`（错误码 + 用户可读信息 + 是否可重试），原始错误只进结构化日志；每次请求一个 id，同时出现在日志、响应头和前端错误消息中。
- **代价**：新增错误场景需要补映射，已用单元测试覆盖主要分支。

## ADR-10 意图路由放在流水线第一位

- **背景**：用户说"你好"时也触发了完整的建站流程。
- **决定**：Mike 先用一次小的 JSON 调用判断是"开发"还是"闲聊提问"，闲聊直接回答并 `halt`。
- **代价**：每次生成多一次模型调用（输出很短），换来不会误改代码，也为以后细分意图（新功能 / 修 bug / 改样式）留了位置。
